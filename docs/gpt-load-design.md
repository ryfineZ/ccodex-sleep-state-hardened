# 从 GPT-Load 学什么，哪些不搬过来

我们要解决的是：群友下载后能接上自己的 Codex，遇到问题知道卡在哪一步，退出后能回到原来的配置。不是把一个本地小工具变成需要维护账号池和数据库的中转平台。

这份对照覆盖本次查看到的主要功能域，不代表「GPT-Load 的全部功能已经移植」。标为待做的功能，不应出现在发布说明的完成列表里；新代码的测试结果以 [测试说明](testing.md) 为准。

## 先把几个容易混淆的词说清楚

- **我们的订阅**通常是代理节点订阅；GPT-Load 的订阅渠道则指 Codex、Claude 等服务的账号授权。不是同一回事。
- **Team 账号识别**与 **API 多凭据池**也不是一回事。这里识别账号类型是为了选择 state 筛选规则，不意味着要导入、轮换整个团队的登录凭据。
- GPT-Load 的 `degradation` 模块使用 ModelTrace 数字采样指纹库。它的 `292–332` 是请求模型输出的数字数量范围，**不是 turn-state 长度规则的证据**。统计归因也不能作为模型身份或「降智」的确定证明。[对应算法与数据来源](https://github.com/DesuwaDev/gpt-load/tree/a4f9f3606b6edf7cd0f1ad6c40b71c3735632804/internal/degradation)
- 「一键配置」不等于静默覆盖已有配置。「无缝切换」不等于在生成到一半时换账号、换模型，再悄悄重放一遍问题。

## 先把本地用户的这条路走通

1. **启动不用猜。** 双击启动脚本，或执行 `ccodex-sleep-state setup`，自动接入并打开浏览器，首页按钮用于再次修复。已有订阅、代理和设置不会被随意重置。若服务 JSON 损坏，会进入只读修复面板：先展示操作，再由用户确认备份并创建默认配置，修复后重新启动。脚本不是安装器，不注册系统服务。
2. **接管结果说清楚。** 区分服务已启动、配置已接管、请求已经过、已有可用 state。四者不能混成一个绿色开关。
3. **切 CCS 不丢配置。** 改了连接或认证时暂停接管，保留双方文件；只改注释等无关内容不应造成整个服务不可用。修复前做备份，冲突由用户明确选择。
4. **采不到就解释。** 账号规则、长度不匹配、网络、未完整回复、冷却和上游拒绝分别显示。Team 的 332 不该再按个人 292 一概拒绝；312/356 也不能改个数字冒充合格。
5. **不会排错也有出口。** 执行 `ccodex-sleep-state doctor`，得到只读摘要。把这份摘要发给群友或 AI Agent，而不是发送自己的配置、订阅链接和登录文件。

启动和 `doctor` 本身不发送模型请求。接管后，用户在 Codex 中开始对话，仍可能触发有预算的 state 采集。初次安装不会自动做真实模型连通性测试。

## 一键启动的验收边界

- 首次配置、安全重复运行、无效配置保留、符号链接拒绝、脱敏报告都有独立测试。
- `--no-config` 适用于 `serve` 和 `setup`，仍然表示不修改 Codex 配置，不会被“一键”绕过。
- 启动脚本需要和对应平台二进制一起打包；源码 checkout 中没有编译产物时会明确提示，不会偷偷下载程序。
- macOS 的系统安全提示需要用户正常授权；脚本不清除隔离属性，不关闭 Gatekeeper。
- 双击 Windows 脚本的实际体验、CCS 不同版本、各中转站、真实 Team 账号与压缩协议都需要各自验收。Sol V2 真实成功不能替代 V1；本轮 V1 直连失败已经记入问题清单。通过单元测试不是“所有环境永远兼容”的证明。
