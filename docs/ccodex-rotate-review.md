## 为什么不能直接照搬模型检测

固定提交 `internal/proxy/server.go` 的响应复制只保留前 `1<<15` 字节，随后调用 `extractModel`；该函数通过字节查找取得第一个 model 字段，没有完整 JSON/SSE 的字段归属或冲突判断。对正常的早期 response.created 可能有用，但模型信息晚到、压缩、多个声明或其他嵌套 model 字段时，可能漏报或误取。

我们的 `internal/modelaudit/model.go` 使用限定字段路径与事件类型，在有界捕获片段内扫描结构化证据，并保留来源、位置、序号和时间；超过前 32 KiB 才出现模型的场景已有回归测试。默认仍只记录每方向前 2 MiB，不是无限捕获，超过范围明确标记受限。

原项目 `internal/modelid/modelid.go` 的内置映射会合并若干不同的产品名，并剥离部分后缀。该规则适合其作者自己的缓存约定，但不适合作为“实际返回模型一致”的通用证明。本次没有移植这些映射。

## 冷却与重试的实现问题

固定提交 `internal/pool/pool.go` 的 `Next` 在所有节点都冷却时仍返回一个候选，削弱了冷却保证。`Degraded` 记录按节点名称保存，没有按凭据、模型、上游作用域分别累计。模型差异可能来自账号或服务端调度，不能直接归因为节点本身。我们的分组统计不对这种因果作推断，可靠转发的熔断也不因模型名不同而触发。

固定提交 `internal/proxy/server.go` 的 `retriableStatus` 包含 403、502、503、504；`retriableErr` 根据错误字符串允许部分连接重置、EOF 等重试。即使没有返回正文，也不能由此证明正式生成未执行。我们不移植正式 POST 自动重放，也不会通过切出口忽略认证或限流决定。记录器如实记录每次客户端请求及上游结果；它本身没有跨请求的账号暂停器，已有可靠转发入口的暂停机制仍保持独立。

其 `ForceModel` 修改出站 model 字段，不等于能保证服务器内部执行指定模型。按最新需求，0.3.1 增加默认关闭的独立强制改写开关，以结构化方式仅替换受支持生成请求的顶层 model 值，并保留改写前后记录。`HuntEnabled` 与周期采集会产生额外模型请求，不属于无副作用观测工具，本次不启用或执行。

## Cookie、时效和订阅值得参考的部分

参考项目新增了 Cookie 与 state 组合新鲜度配置；这说明需要观测 Cookie，而不仅是 state 的长度。但固定的 240 秒只是该项目的配置策略，不能作为服务端 TTL 的事实。我们的记录器原样转发客户端 Cookie，保留脱敏关联指纹；可靠转发入口仍使用单独的 Cookie 生命周期组件。

`internal/mihomo/manager.go` 的 `PrepareProviders` 在订阅下载失败、无缓存时记录告警并继续其他来源，这是值得在将来的订阅加载层吸收的容错设计。独立记录器目前只使用一个明确配置的上游和可选网络代理，不增加订阅控制面。
